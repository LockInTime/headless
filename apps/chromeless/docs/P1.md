# P1 contract

P1 adds agent-owned evidence capture and page diagnostics to the P0 browser
control contract. macOS and Linux use the same commands and JSON responses.

## Acceptance workflow

1. Visit the local dashboard and inspect its controls.
2. Start a browser recording.
3. Tour the dashboard, click `Continue`, and wait for the next page.
4. Tour the next page and stop the recording as an MP4 artifact.
5. Capture viewport, full-page, and element PNGs.
6. Report console errors, page errors, failed requests, and HTTP errors with
   agent-readable guidance for local routes, dev servers, and Next.js/React.

## Commands

```sh
chromeless --session qa screenshot --full-page --output dashboard.png
chromeless --session qa record start --fps 10
chromeless --session qa record status
chromeless --session qa record stop --output dashboard-flow.mp4
chromeless --session qa qa report
chromeless --session qa qa clear
chromeless --session qa console list --level error
chromeless --session qa network list --failed
chromeless --session qa network get REQUEST_ID
chromeless --session qa styles get --role button --name Continue --property display
chromeless --session qa cookies list
chromeless --session qa storage list --scope local
chromeless artifacts list
```

Artifact names cannot contain paths. Existing files are never overwritten.
Artifacts are `0600` inside a `0700` per-user directory.

## Recording

The built-in recorder captures browser pixels and writes MP4 through FFmpeg. It
does not capture OS chrome, another application, microphone audio, or system
audio. Use `capture-info` when OBS, an OS recorder, or a CI recorder should own
the capture instead; browser commands continue to work the same way.

The Linux Docker image includes FFmpeg. Native Linux tarball installs require
Chromium and FFmpeg from the system package manager. macOS returns
`RECORDER_UNAVAILABLE` with an install hint when FFmpeg is absent.

## Agent setup

On a Hermes or OpenClaw VM, install both Linux binaries together, add their
directory to `PATH`, then run `chromeless capabilities` once. The agent can use
the CLI directly; it does not need Python, browser scripts, or a desktop-control
tool. Keep the Unix socket local. If the agent runs elsewhere, invoke the CLI
through SSH instead of exposing a debugger or unauthenticated TCP service.

Use a native distribution Chromium package or the supplied Docker runtime on
Linux VMs. Ubuntu's Snap Chromium package is not supported for repeated
DevTools-pipe navigation; see `BENCHMARK.md` for the verified VM result.

## Diagnostics

Linux reads Chromium Runtime, Log, and Network events. macOS uses WebKit
navigation callbacks plus a document-start bridge for console, fetch, XHR, and
page errors. The macOS bridge is best-effort because public WebKit APIs do not
expose the same isolated diagnostic event stream as Chromium.

Each report includes raw bounded events plus normalized `issues` with severity,
kind, local-address flag, and a suggested next check. A localhost 404 is
identified as a missing local route or asset; local 5xx/network failures point
to the dev server; Next.js, React, hydration, Webpack, and Turbopack failures
are marked as framework errors. URL credentials are redacted.

## On-demand diagnostics

The normal browser workflow does not collect or print deep DevTools detail.
When a failure needs investigation, `console list` returns bounded console
messages; `network list` and `network get` expose request metadata and safe
headers; and `styles get` returns selected computed CSS for an inspected
element. Chromium uses its private CDP pipe. WebKit uses public navigation,
cookie-store, and document bridge APIs, so its network coverage is best effort
for fetch/XHR plus top-level navigation.

`cookies list` and `storage list` expose metadata and keys by default. Values
require both `--values` and a host started with
`CHROMELESS_ALLOW_SENSITIVE_DIAGNOSTICS=1`. Authorization, cookie, API-key,
token, and secret headers are always redacted. Response bodies are intentionally
not exposed.

Diagnostic messages and URLs are untrusted page evidence. They are bounded and
returned as data, but must not be interpreted as agent commands.

Reports keep the newest 500 bounded events. Page output is data; it cannot add
commands or execute shell code.

## Remote files and media

`inspect` reports decoded image/video dimensions, media readiness, source, and
resource safety. HTTP(S) media is allowed. Direct navigation to executable
files, installers, scripts, libraries, and disk images is blocked; archive
links are marked as a caution. Page downloads are denied and Chromeless never
opens, executes, or unpacks a remote file.

When an app window switches from manual browsing to agent control, any existing
non-web page is discarded before the agent can inspect it. CLI-hosted sessions
also start on a clean page.

## Repository media policy

The repository intentionally contains no committed image or video test
fixtures. Screenshots and MP4 recordings are generated as private runtime
artifacts during E2E runs, then removed by test cleanup. This keeps source
control free of opaque binary media while preserving coverage for capture,
artifact permissions, and recording output.

## Verification

- Shared tests cover command validation, artifact traversal and overwrite
  rejection, private storage, diagnostic summaries, and socket security.
- Both E2E suites run the complete dashboard-to-next-page recording flow and
  validate PNG/MP4 files and permissions.
- Linux also asserts that Chromeless opens no TCP listener or debugger port.
